# Feature Specification: 记账条目可选时间与按时间排序

**Feature Branch**: `20261008-225439-entry-time-sort`

**Created**: 2026-10-08

**Status**: Draft

**Input**: User description: "阶段详情页面，大额页面，新增条目时可以填写时间（可选），并且列表展示根据时间顺叙展示，需要兼容之前没有填写时间的数据，不填时间就按照创建时间顺序，比如依次创建4天数据，0：不填创建时间，1：创建时间为10月9，2：不填创建时间，3：创建时间为10月8号，那顺序为0-3-1-2"

## Clarifications

### Session 2026-10-08

- Q: 两个目标页面上共有 6 个「新增条目」表单（各 1 个「追加」+「个人支出」+「其他支出」），时间字段加在哪些上？ → A: **6 个表单全部支持**。与「两个页面的新增条目」的字面口径一致，两个页面的追加列表也获得同样的排序能力；规则统一，用户无需记忆差异。
- Q: 时间精度是仅到「日」，还是到「日 + 时分」？ → A: **仅到「日」**。与示例中「10月8号」「10月9」的表述一致，输入成本最低。已知代价：同一天内的多条记录无法靠时间区分先后，只能由手工拖拽排列。
- Q: 两个页面的列表当前都支持长按拖拽手工排序（写回 `sort_order`），改为按时间排序后拖拽会被立刻覆盖，如何取舍？ → A: **保留拖拽，且未填写时间的条目可以无条件任意拖动**（不受任何日期约束，可拖到列表任意位置）；**已填写时间的条目只能在同一天内拖动**。
- Q: 未填写时间的条目既然要求「无条件任意拖动」，那它们是否仍按创建时间参与全局排序？ → A: **不参与**。这一条答复实际上确定了整个排序模型：**列表顺序是一个被持久保存的位置值，时间只在「新增 / 修改时间」时决定该条目落到的位置**（见 FR-003）。若未填写时间的条目按创建时间参与全局排序，它们就会被创建日期锁定在固定的日期组内，无法任意拖动；二者不可兼得，以「任意拖动」为准。该模型同时精确复现了文首示例 0-3-1-2——在**同一天**依次录入这 4 条即可得到，无需假设创建跨天。

## 排序模型（本特征的核心约定）

每一条条目在列表中拥有一个**位置**，列表按位置从前到后展示。位置在条目创建时确定，此后只被两件事改变：

1. **新增或修改该条目的时间** → 按 FR-003 重新落位；
2. **用户手工拖动** → 按 FR-011 的约束改写位置。

「时间」字段本身**不直接参与排序比较**，它只在上述第 1 条中作为落位依据。这样设计的原因：用户要求未填写时间的条目「无条件任意拖动」，而这与「时间直接决定排序」在机制上互斥——任何由日期派生的排序键都会把无时间的条目钉死在某个日期区间，拖不走。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新增条目时可选填写发生时间 (Priority: P1)

用户在「阶段详情页」或「大额页」新增一条记账条目（支出或追加）时，除了既有的金额与描述，还可以**可选地**指定这笔记录实际发生的日期。不填时，整个新增流程与现在完全一样——不增加任何必填项、不增加任何额外点击。

**Why this priority**: 这是整个特性的数据入口。没有它，后续的落位与拖动规则无数据可依。仅交付这一条，用户至少可以把时间补录进系统，其价值可独立验证。

**Independent Test**: 在阶段详情页展开「个人支出」新增表单，只填写金额与描述、不填时间并确认添加，条目正常保存；再次新增一条并额外选择一个日期，条目同样正常保存且携带该日期。

**Acceptance Scenarios**:

1. **Given** 用户在阶段详情页展开「个人支出」新增表单，**When** 只填写金额与描述、不填时间后确认添加，**Then** 条目成功保存，新增流程的操作步骤与改动前一致。
2. **Given** 同上，**When** 额外选择一个日期后确认添加，**Then** 条目成功保存并携带该日期，表单在提交后清空（含时间字段）。
3. **Given** 用户在大额页展开任一新增表单，**When** 填写金额与描述并选择一个日期后确认添加，**Then** 条目成功保存并携带该日期。
4. **Given** 用户在新增表单中已选择了一个日期，**When** 用户清除该选择后确认添加，**Then** 条目以「未填写时间」的状态保存。

---

### User Story 2 - 填写时间的条目自动落到对应日期位置 (Priority: P1)

用户在录入一笔旧账时填上它实际发生的日期，这条记录会立刻落到列表中该日期应该在的位置，而不是被追加到末尾。列表整体因此呈现「按时间顺叙」的观感。

**Why this priority**: 这是本特性对用户可见的全部收益——填写时间的目的就是让记录出现在正确的位置。它与 User Story 1 共同构成最小可用闭环，缺一不可。

**Independent Test**: 在任一列表新增一条填写了较早日期的记录，确认它出现在列表中对应的位置而非末尾；再新增一条不填时间的记录，确认它被追加到末尾。

**Acceptance Scenarios**:

1. **Given** 列表中已有若干条目，**When** 用户新增一条填写了某日期的条目，**Then** 它落在列表中第一个「时间晚于该日期」的条目前面；若不存在这样的条目，则落在末尾。
2. **Given** 列表中存在若干条目，**When** 用户新增一条「未填写时间」的条目，**Then** 它被追加到列表末尾（与改动前的行为一致）。
3. **Given** 一条已保存的条目，**When** 用户把它的时间改成一个更早的日期，**Then** 该条目按第 1 条规则重新落到更靠前的位置。
4. **Given** 一条已保存的条目，**When** 用户把它的时间清空，**Then** 它停在当前位置不再移动，并恢复为可任意拖动。
5. **Given** 文首示例的录入序列（0 未填、1 填 10月9、2 未填、3 填 10月8，**同一天依次创建**），**When** 录入完毕，**Then** 列表顺序为 **0-3-1-2**。

---

### User Story 3 - 手工拖动调整顺序 (Priority: P2)

用户长按条目拖动可以调整列表顺序。未填写时间的条目可以拖到任何地方；填写了时间的条目受日期约束，只能在自己那一天的前后范围内移动。

**Why this priority**: 这是既有能力的延续与收紧。没有它，列表顺序完全由录入顺序决定，用户无法纠正；但它不阻塞前两个故事的价值交付。

**Independent Test**: 在同一批未填写时间的条目中任意拖动一条到其他位置，确认顺序立即改变并保持；再把一条填写了时间的条目拖向其日期范围之外，确认它不会被移出。

**Acceptance Scenarios**:

1. **Given** 一条未填写时间的条目，**When** 用户长按并拖到列表中的任意位置（包括两条已填写时间的条目之间），**Then** 新顺序立即生效并在刷新后保持。
2. **Given** 若干条同一天（同一时间值）的条目，**When** 用户在它们之间调整先后，**Then** 调整立即生效并在刷新后保持。
3. **Given** 一条填写了日期的条目，**When** 用户尝试把它拖到日期晚于它的条目之后，**Then** 该拖动 MUST NOT 生效，用户得到可感知的反馈而非「拖了没反应」。
4. **Given** 一条填写了日期的条目，**When** 用户尝试把它拖到日期早于它的条目之前，**Then** 同样 MUST NOT 生效。

---

### User Story 4 - 历史数据无损兼容 (Priority: P2)

升级前已存在的条目全部没有填写时间。升级后它们既不能丢失、也不能乱序——它们仍按创建先后排列，与升级前的观感一致。

**Why this priority**: 本地数据没有服务端兜底，任何一条历史记录丢失或错位都是不可接受的。但它不需要用户做任何操作，是一条被动的、可独立验证的保障。

**Independent Test**: 用一份只含「未填写时间」记录的旧数据库启动应用，确认所有记录条数不变、顺序与升级前一致。

**Acceptance Scenarios**:

1. **Given** 一个升级前创建的数据库，其中的条目全部没有时间，**When** 应用升级后打开任一列表，**Then** 全部条目仍在、顺序与升级前完全一致。
2. **Given** 一份由旧版本导出的备份文件（不含时间字段），**When** 用户导入，**Then** 导入成功，这些条目按「未填写时间」处理。
3. **Given** 一份由新版本导出的备份文件（含时间字段），**When** 用户导入，**Then** 时间与列表顺序都被完整还原。

---

### Edge Cases

- **填写了未来日期**：允许。条目落到列表末尾方向，不做拦截。
- **填写了不属于当前阶段/周期时间范围的日期**：允许。时间字段是用户自由填写的记录属性，不做跨表校验。
- **同一天内新增多条且都填了当天日期**：它们的落位依据相同，按录入先后挨在一起，顺序稳定。
- **新增表单提交后**：时间字段必须一并重置为空，避免连续新增时把上一条的日期带到下一条。
- **导入的备份缺少时间字段**：按「未填写时间」处理，不报错。
- **导入的备份缺少位置字段**：按原顺序（或创建先后）补位，不报错。
- **把已填写时间的条目清空时间**：停在当前位置，并恢复为可任意拖动。
- **列表中已无「时间晚于 X」的条目时新增一条日期为 X 的记录**：落在末尾。
- **记录被删除后**：其余条目的相对顺序 MUST NOT 改变。
- **拖动未填写时间的条目穿过若干日期组**：允许，日期组不构成屏障。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 阶段详情页与大额页上的**全部 6 个新增条目表单**（各页面的「追加」「个人支出」「其他支出」）MUST 提供可选的时间字段；字段留空时，新增流程的必填项数量与操作步骤 MUST 与改动前完全一致。
- **FR-002**: 时间字段 MUST 可选，默认值为空；MUST NOT 以「默认为今天」等方式使其实际成为必填。时间精度 MUST 为「日」，不含时分。
- **FR-003**: 每条条目 MUST 在列表中拥有一个持久保存的位置。新增条目时，其初始位置 MUST 按以下规则确定：
  - **填写了时间**：落在列表中第一个「时间晚于该日期」的条目**之前**；若不存在这样的条目，则落在末尾。「比它早」的定义仅在同为已填写时间的条目之间比较。
  - **未填写时间**：追加到列表末尾。
- **FR-004**: 用户修改一条条目的时间时，该条目 MUST 按 FR-003 的规则重新落位；清除时间时 MUST 停在当前位置不动。
- **FR-005**: 列表 MUST 按位置从前到后展示。未填写时间的条目 MUST NOT 被时间排序规则强制归位——其位置只由创建时的追加与用户手工拖动决定。
- **FR-006**: 升级前已存在的条目（未填写时间）MUST 无需用户操作即可保持其既有顺序，条数 MUST NOT 减少、顺序 MUST NOT 与升级前产生差异。
- **FR-007**: 时间字段 MUST 支持在编辑已有条目时修改，也 MUST 支持被清空。
- **FR-008**: 导出/导入的备份结构 MUST 保持向后兼容：缺少时间字段的旧备份 MUST 能被导入并按「未填写时间」处理；含时间与位置信息的新备份 MUST 能完整还原。
- **FR-009**: 涉及的数据结构变更 MUST 通过版本递增与既有迁移机制完成，MUST NOT 以删表重建的方式处理已有数据。
- **FR-010**: 时间字段的填写 MUST NOT 影响任何金额统计口径（小计、合计、余额、饼图构成等）。
- **FR-011**: 条目列表 MUST 保留长按拖拽排序能力，并按是否填写时间区别约束：
  - **未填写时间**的条目：MUST 可被拖到列表中的**任意位置**，不受任何日期约束。
  - **已填写时间**的条目：MUST 仅在**同一天**（同一时间值）的条目之间调整先后。判定标准：拖动完成后，该条目**前方不得出现时间晚于它的条目，后方不得出现时间早于它的条目**。
  - 被拒绝的拖动 MUST 给出可感知的反馈，MUST NOT 让用户处于「拖了但看起来没生效」的状态。
- **FR-012**: 删除任意条目后，其余条目的相对顺序 MUST NOT 改变。

### Key Entities *(include if feature involves data)*

- **记账条目（支出）**：一笔具体消费。既有属性：所属阶段或周期、分类、金额、描述、创建时间、排序序号。本次新增属性：**发生时间（可空，日粒度）**。
- **记账条目（追加）**：一笔资金追加。既有属性：所属阶段或周期、金额、原因、创建时间、排序序号。本次新增属性：**发生时间（可空，日粒度）**。
- **位置**：条目在列表中的持久顺序。既有实现已存在一个排序序号字段，本次改动的要点是**它成为唯一的列表顺序来源**，而时间字段退居为「落位依据」。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 不填写时间的记账流程，其点击/输入步骤数与改动前**完全相同**（零新增步骤）。
- **SC-002**: 按文首示例依次录入 4 条（0 未填时间、1 填 10月9、2 未填时间、3 填 10月8，**均在同一天录入**），列表顺序 MUST 为 **0-3-1-2**。
- **SC-003**: 升级后历史条目**零丢失、零错序**：未填写时间的条目在列表中的顺序与升级前逐条一致。
- **SC-004**: 新增或修改一条记录后，列表重排结果在 1 秒内可见，用户无需手动刷新。
- **SC-005**: 未填写时间的条目可以在一次拖动内到达列表中**任意**位置，无一例被拒绝。
- **SC-006**: 已填写时间的条目，其拖动被日期约束拒绝时，用户 MUST 在 **1 秒内**看到明确反馈。

## Assumptions

- **时间精度为「日」**：已由 Clarifications 确认。时间字段精确到日期，不含时分；同一天内的先后完全由手工拖拽决定。
- **列表顺序由一个持久化的排序序号承载**：既有代码中该字段已存在（新增时取最大值 +1），本特征改变的是它在排序中的地位，而非引入全新字段。具体承载方式在实现方案中确定。
- **时间字段在新增与编辑时都可用**：否则用户填错后无法纠正。
- **时间字段在列表条目上可见**：否则用户填写后无法感知其效果，也无从判断某条为何落在该位置。
- **不校验时间与所属阶段/周期的时间范围是否匹配**：允许自由填写，避免因阶段的起止日期变更导致既有数据被判定为非法。
- **未填写时间的条目行为与改动前基本一致**：新增时仍追加到末尾、仍按录入先后排列；差别仅在它们现在可被任意拖动。
- **金额口径不受影响**：时间只是落位与展示属性，不参与任何统计计算。
