# APK 体积优化计划

## 目标与边界

- 在不改变现有业务功能、数据结构、权限和可支持设备范围的前提下，降低 Android 发布包的下载体积。
- 当前基线：`build/app/outputs/flutter-apk/app-release.apk` 为 57,880,032 字节（约 55.2 MiB）。
- 优先优化用户实际下载的包体积；如仍需提供单个通用 APK，则同时保留该产物并明确其与分架构 APK 的体积差异。
- 不移除模块、第三方能力或必要资源；不修改现有未提交的业务代码。

## 已确认现状

- `android/app/build.gradle.kts` 的 `release` 构建类型目前只配置了签名，未启用 `minifyEnabled`、`shrinkResources` 或 ABI 分包。
- 项目没有 Flutter `assets` 目录资源；Android 启动图和图标资源合计极小，非主要优化目标。
- 依赖中包含多个带原生实现或会增大 Dart AOT 代码体积的库（例如 SQLite、文件选择、二维码、图表、网络与本地服务相关库），需先用构建分析确认实际占比，不能仅凭依赖名删除。

## 实施步骤

1. 建立可复现的体积基线
   - 使用同一 Flutter SDK 与 release 参数重新构建，记录通用 APK 的大小、构建命令和 Git 提交状态。
   - 运行 Flutter 的体积分析构建，导出包内容/代码体积分解结果，分别识别 Dart AOT、Flutter 引擎、各 ABI 原生库、资源和第三方代码的占比。
   - 分别构建 `arm64-v8a`、`armeabi-v7a`、`x86_64` APK，量化“多 ABI 合包”产生的额外体积。

2. 采用面向发布渠道的分发产物
   - 若发布到 Google Play 或其他支持 App Bundle 的商店，改为发布 AAB；商店会按设备 ABI 下发拆分包。
   - 若通过下载页/私域直接安装，生成并提供 ABI 拆分 APK，并在下载页清晰标注架构；同时按需要保留通用 APK 作为兼容兜底。
   - 不改变运行时功能、权限或最低系统版本，仅改变构建与交付方式。

3. 开启安全的 release 收缩
   - 在 Android release 构建中启用 R8 代码压缩与 Android 资源收缩。
   - 为 Flutter 插件、反射调用、Android manifest 组件和 JNI 相关项补充最小化 keep 规则；以运行验证结果为准，避免误裁剪。
   - 对比开启前后的分析报告，确认实际收益来自可安全删除的 Java/Kotlin 与 Android 资源，而非错误排除了必要功能。

4. 基于分析报告精简可替代依赖与资源
   - 逐项核对大体积依赖是否在生产代码中实际使用，并结合调用链确认替代或移除的影响范围。
   - 对仅为桌面端兼容引入的依赖，评估通过平台条件实现或 Android 侧剔除的可行性；前提是 Windows 功能保持可用。
   - 检查字体、图片和 Android 资源的实际引用；仅压缩冗余或可无损/视觉等价替换的资源。
   - 每次只处理一项，并重新构建、比较体积和回归测试，确保收益可归因。

5. 验证与交付
   - 执行静态分析与测试；在 Android 真机/模拟器验证启动、记账、生理期记录、图表、导入导出、文件选择、二维码、外链等现有路径。
   - 输出优化前后对比：通用 APK、各 ABI APK、AAB 的大小和比例；记录推荐发布方式与回滚方式。
   - 将构建命令写入项目文档或发布说明，确保后续发版持续获得相同收益。

## 验收标准

- 所有现有自动化测试和静态分析通过，重点业务链路人工验证通过。
- 通用 APK 不大于当前基线；分架构 APK/AAB 的设备实际下载包显著小于当前通用 APK。
- 体积报告能说明每项优化的收益，且 release 收缩不引入崩溃、功能缺失或数据兼容问题。

## 风险与决策点

- ABI 分包能带来通常最大的下载体积下降，但需要发布渠道支持或用户选择正确架构；若必须只提供一个 APK，收益会受限。
- R8/资源收缩可能误删经反射或插件间接使用的类与资源，因此必须先分析、再逐项验证并保留可回滚配置。
- 依赖精简应以体积分析和实际引用为依据；不能为了减包删除 Windows 或 Android 的既有能力。
